# Restore and rollback

**Backup:** `npm run restore:rehearsal` creates `data/backups/<stamp>/` (database via `VACUUM INTO` + media copy), restores it into `data/restore-test/<stamp>/`, opens it, checks integrity (audit chain, no double credits, no orphan entries, draws recompute, media present), lists outstanding jobs/outbound work, and reports RTO. Production: schedule the backup step at ≤15-minute intervals to an off-host location (Railway volume snapshots or object storage).

**Restore:** stop the service; copy the backup database and media into place; start; the worker resumes leases and outstanding jobs; idempotency keys prevent double messages/awards; run `GET /api/audit/verify` and the draw verifier for any executed draws.

**Rollback of a release:** deploy the previous artifact; everything from 007 onward is compatible with the previous code — there was never a rebuild of `draws` (the plan was rejected, ADR-0007), so do not go looking for one. What 008–012 actually did is listed in `docs/release/migrations.md`: a partial UNIQUE index on `audit_events(prev_hash)`; the nullable `draws.seed_commitment`; `canonical_receipts.receipt_no_norm` with its index; `admin_users.mfa_pending_secret` with the `idx_receipts_media` and `idx_entries_period_code` hot-path indexes; and two index drops (`idx_entries_draw`, `idx_receipts_processing`). Three of those steps are not additive and each is safe to leave in place: 011 also DELETEs the dead `retention_*` rows from `schema_meta` (both releases read retention from the environment, so neither misses them), and 012's two drops remove indexes measured as never chosen by any query plan — the previous release runs correctly without them, and either can be re-created from `db/migrations/012_drop_unused_indexes.sql` if a plan regression shows up. No column, table or row of application data is removed by any of them; nothing needs reverting by hand. Reverting code never removes entries or reseeds prizes.
